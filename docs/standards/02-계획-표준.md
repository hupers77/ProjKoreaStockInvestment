# 02. 기획·계획 표준

> 적용 대상: 주식·채권·환율·가계부·연금·포트폴리오 등 경제·금융 관련 프로그램
> 산출물: 기획서 1장 + 판단 규칙서 + 데이터 소스 표 + 마일스톤 + 위험 목록 + 결정 기록

---

## 1. 기획서 (1~2쪽)

| 항목 | 작성 내용 | 이번 프로젝트 예 |
|---|---|---|
| 문제 | 지금 무엇이 불편한가 | 매일 2,700개 종목을 직접 볼 수 없음 |
| 목표 | **측정 가능한** 결과 | (개선) "B등급 이상 종목의 6개월 평균 수익률이 KOSPI보다 높다" |
| 사용자 | 누가, 언제, 어디서 | 개인 투자자 1명, 평일 저녁, 맥북 |
| 의사결정 | 이 프로그램이 돕는 판단 | 매수 후보 선정, 보유 종목 경고 |
| 범위 | 하는 것 / 하지 않는 것 | 자동 매매 안 함, 다중 사용자 없음 |
| 성공 기준 | 출시 판단 기준 | 실데이터 스캔 성공, 등급 분포 확인, 백테스트 결과 |
| 제약 | 비용, 데이터, 법 | 무료 데이터만, 개인용 |

### 목표 작성 규칙
- "손실 없는", "무조건 오르는" 같은 표현을 쓰지 않는다. 금융에서 보장된 결과는 없다.
- 수익률·적중률·최대 낙폭·변동성 중 무엇을 개선할지 고르고, **비교 대상(벤치마크)** 을 정한다 (KOSPI, KOSDAQ, 예금 금리).
- 판단 보조 도구인지, 자동 실행 도구인지 명시한다.

## 2. 판단 규칙서 (가장 중요)

코드보다 먼저 만든다. 이번 프로젝트의 `korean-stock-scoring-framework.md`가 좋은 예다.

필수 구성:
1. 관점·기간 정의 (단기/중기/장기)
2. 항목별 지표, 점수 구간, 가중치 (관점별 합 100)
3. 제외 조건(Knock-out)
4. 가점·감점
5. 등급 구간과 게이트(커버리지 등)
6. 업종별 예외 (금융·지주·리츠 등)
7. 데이터 처리 규칙: 기준일, 결측(N/A), 추정값 상한, 이상치
8. 계산 예시 1개 이상
9. **버전 번호와 변경 이력** (v1.0 → v1.1)

**[보강] 이번에 빠졌던 것**
- 항목별 "무료로 구할 수 있는가" 표를 기준서 작성 단계에서 같이 만든다. 이번에는 구현 후에 커버리지가 50~65%뿐이라 A·S 등급이 거의 안 나온다는 것을 알게 되었다.
- 기준값(커버리지 70%/80% 등)은 **실데이터로 등급 분포를 본 뒤 확정**하는 단계를 둔다.
- 기준서와 실제 구현이 다른 부분은 "편차표"로 관리한다 (README 4장처럼).

## 3. 데이터 소스 표

| 데이터 | 출처 | 비용 | 인증 | 갱신 시각 | 과거 조회 | 재배포 가능 | 안정성 | 대체 경로 |
|---|---|---|---|---|---|---|---|---|
| 일별 시세 | pykrx(KRX) | 무료 | KRX 계정 | 장 종료 후 | 가능 | 확인 필요 | 응답 형식 변경 잦음 | FinanceDataReader |
| 재무제표 | OpenDART | 무료 | API 키 (일 20,000건) | 공시 시 | 가능 | 공공데이터 | 계정명이 회사마다 다름 | - |
| 관리종목 | FDR | 무료 | 없음 | 수시 | 현재만 | 확인 필요 | 보통 | KIND |

작성 규칙:
- 항목마다 **대체 경로**를 정한다. 없으면 N/A 처리 방침을 정한다.
- **과거 시점 조회 가능 여부**를 반드시 쓴다. 백테스트가 가능한지가 여기서 갈린다 (예: 과거 관리종목 목록은 없음).
- 호출 한도와 첫 수집 소요 시간을 추정한다 (이번: 첫 스캔 10~30분, DART 추가 시 30~60분).
- 데이터 이용 약관(개인 사용/재배포/상업적 이용)을 확인한다. → [08-금융 도메인](08-금융-도메인-체크리스트.md)

## 4. 마일스톤 (권장 순서)

| 단계 | 산출물 | 완료 기준 |
|---|---|---|
| M0 기획 | 기획서, 판단 규칙서 v1, 데이터 소스 표 | 사용자 확인 |
| M1 데이터 스파이크 | 실데이터 1일치 수집 스크립트, 응답 표본 저장 | **사용자 PC 또는 실제 망에서 성공** |
| M2 계산 엔진 | 채점 엔진 + 단위 테스트 | 기준서 계산 예시와 일치 |
| M3 화면 시안 | 주요 화면 와이어프레임/시안 | 사용자 선택 |
| M4 v1 | 수집·계산·화면·스케줄러 | 실데이터 스캔 1회 성공 |
| M5 보정 | 등급 분포, 커버리지 확인, 기준값 조정 | 분포가 의도와 맞음 |
| M6 검증 | 백테스트 (여러 기준일) | 검증 보고서 |
| M7 운영 | 자동 실행, 알림, 백업, 버전 표시 | 1주 무인 운영 |

이번 프로젝트는 M1·M3·M5를 건너뛰고 M4로 갔다. 결과적으로 M1 문제(실데이터 오류)와 M3 문제(표시 방식 반복 변경), M5 문제(A·S 거의 없음)가 출시 후에 나타났다.

## 5. 위험 목록 (시작 시 작성, 주 1회 갱신)

| 위험 | 가능성 | 영향 | 대응 |
|---|---|---|---|
| 데이터 소스 응답 형식 변경 | 높음 | 스캔 실패 | 대체 경로, 버전 고정, 오류 메시지에 단계 표시 |
| 개발 환경에서 실데이터 접근 불가 | 높음 | 출시 후 버그 | 사용자 PC 스모크 테스트, 응답 녹화 |
| 백테스트 과최적화 | 중간 | 잘못된 확신 | 표본 외 기간 검증, 다중 기준일 |
| 자격 증명 유출 | 낮음 | 계정 도용 | 키체인/환경 변수, 저장소 제외 |
| 시장 규칙 변경 (거래 시간 등) | 중간 | 스캔 시각 오류 | 설정으로 분리 |
| 법적 이슈 (배포 시 투자자문 해당 여부) | 배포 시 | 큼 | 공개 전 검토 |

## 6. 결정 기록 (ADR)

결정마다 한 줄씩 남긴다. 다음 대화나 다른 개발자가 같은 질문을 반복하지 않게 한다.

```
| 날짜 | 결정 | 이유 | 대안 | 결정자 |
| 10/02 | 투자검증은 현재 평가 기준을 과거 데이터에 적용 | 현재 기준이 과거에 맞았는지 보려는 목적 | 기준 이력 관리 | 사용자 |
| 10/02 | 공매도 잔고 항목 제외 (S11 N/A) | KRX 응답 불안정 | 다른 출처 | 사용자 |
| 10/02 | 스캔 내부 키는 숫자 유지, 화면은 순번 | 기존 데이터 보존 | yymmdd-seq 키 | Claude 제안, 사용자 동의 |
```

## 7. 작업 분할 규칙

- 기능 하나 = 작업 단위 하나(스레드/브랜치/PR). 이번에는 한 스레드에 모든 작업이 쌓여 77개 답글이 되었다.
- 큰 기능(투자검증 같은)은 "데이터 → 계산 → 화면 → 검증" 4단계로 나눠 중간 확인을 받는다.
- 화면만 바꾸는 작은 요청은 모아서 하루 1회 반영해도 된다.
