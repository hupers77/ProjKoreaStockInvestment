# 03. 시스템 설계 표준

> 대상: 데이터를 모으고, 계산하고, 화면에 보여주는 경제·금융 프로그램
> 이번 프로젝트 구조를 기준 모델로 삼고, 부족했던 부분을 [보강]으로 표시했다.

---

## 1. 기본 구조: 수집 · 저장 · 계산 · 표시 분리

```
[스케줄러] ──▶ [수집기 collector] ──▶ [원천 데이터 저장소 / 캐시]
                     │                         │
                     ▼                         ▼
              [기준일 묶음 bundle]  ──▶  [계산 엔진 scoring]  ──▶ [결과 저장 (스캔 기록·점수)]
                                                                    │
                                                    [웹 화면 / 내보내기 / 알림] ◀─┘
```

| 계층 | 책임 | 이번 프로젝트 파일 | 규칙 |
|---|---|---|---|
| 수집 | 외부 API 호출, 재시도, 대체 경로 | `collector.py`, `dart.py` | 화면 코드에서 외부 API를 직접 부르지 않는다 |
| 저장 | 원천 데이터·캐시·결과 | `db.py` (SQLite), `data/*.pkl.gz` | 원천과 계산 결과를 분리 저장 |
| 묶음 | 기준일 시점의 입력 전체 | `bundle.py` | 계산 엔진의 유일한 입력 |
| 계산 | 순수 함수 (입력 → 점수) | `scoring.py`, `framework.py` | 네트워크·DB 접근 금지 → 테스트 쉬움 |
| 표시 | 화면, 내보내기 | `web.py`, `templates/`, `export.py` | 계산하지 않고 결과만 읽음 |

**좋았던 점**: bundle을 파일로 저장해 두어서 "재계산(데이터 조회 없이 다시 채점)"과 "검증 계산"이 쉽게 만들어졌다.
**원칙**: 계산 엔진은 `점수 = f(기준일 묶음, 설정, 기준서 버전)`인 순수 함수로 만든다. 같은 입력이면 항상 같은 결과.

## 2. 시점(Point-in-Time) 설계 — 금융 프로그램의 핵심

모든 데이터에 **세 가지 날짜**를 구분한다.

| 날짜 | 의미 | 예 |
|---|---|---|
| 기준일 (as-of) | 그 값이 "언제 기준"인가 | 2026-06-30 분기 재무 |
| 공개일 (available) | 시장이 **언제 알 수 있었나** | 2026-08-14 분기보고서 제출 |
| 수집일 (fetched) | 우리가 언제 받았나 | 2026-10-02 20:35 |

- 백테스트에서는 **공개일 ≤ 평가 기준일**인 데이터만 쓴다. 이번에는 공개일을 "분기말 + 47일" 같은 기한으로 근사했다. [보강] 가능하면 DART 접수일(`rcept_dt`)을 저장해서 실제 공개일을 쓴다.
- 장중에 받은 값은 미확정이다. 이번에 "20:30 이전에 받은 값은 다음 스캔에서 다시 받기" 규칙을 넣었다. [보강] 확정 여부를 `is_final` 같은 컬럼으로 명시한다.
- 현재 시점에만 있는 데이터(관리종목 목록, 업종 분류, 수동 입력)는 과거 계산에 쓰면 **미래 정보**가 된다. 표시하거나 제외한다.

## 3. 데이터 모델 표준

### 3-1. 필수 테이블 (예시)

| 테이블 | 키 | 주요 컬럼 | 비고 |
|---|---|---|---|
| `prices` | (종목, 날짜) | 시가·고가·저가·종가·거래량·거래대금, `adj_factor`, `is_final` | [보강] 수정주가 계수 |
| `fundamentals` | (종목, 보고서기간, 보고서종류) | 계정값, `rcept_dt` | 공개일 저장 |
| `snapshots` | (기준일, 종류) | 시총·PER·수급 등 기준일 값 | 같은 기준일 재수집 방지 |
| `scans` | id | 종류(live/bt/recalc), 기준일, 프로파일, 상태, 소요시간, **기준서 버전**, **코드 버전** | [보강] 버전 |
| `scores` | (스캔, 종목) | 관점별 점수, 최종 점수, 등급, 커버리지, 제외 사유 | |
| `item_scores` | (스캔, 종목, 항목) | 점수, 원천값, 추정 여부 | 설명 가능성 |
| `holdings` / `exclusions` | 종목 | 매수가·수량·메모 / 사유, **등록일** | [보강] 거래 이력 |
| `settings` | key | 값 | 비밀값은 저장하지 않음 |

### 3-2. 숫자 규칙
- 금액: 원 단위 정수(`INTEGER`). 화면에서만 억·조 단위로 바꾼다.
- 비율: 소수(0.0523)로 저장하고 화면에서 %로. 저장 단위와 표시 단위를 컬럼 이름이나 주석으로 밝힌다.
- 가격 계산에 이진 부동소수점 오차가 문제가 되는 경우(정산·세금·잔고)는 `Decimal`을 쓴다. 점수·지표 계산은 `float`로 충분하다.
- **DB에 쓰기 전 numpy/pandas 타입을 파이썬 기본 타입으로 바꾼다.** 이번 시가총액 bytes 버그의 원인.
- 결측은 `NULL`. 0과 결측을 섞지 않는다 (거래량 0은 거래정지라는 의미가 있다).

### 3-3. 시간 규칙
- 서버·스케줄러는 `Asia/Seoul`로 고정한다 (이번 구현은 지켜짐).
- 날짜는 `YYYY-MM-DD` 문자열 또는 date 타입으로 저장, 화면에서 `YY/MM/DD`.
- 거래일 여부는 요일이 아니라 **거래소 달력**으로 판단한다. [보강] 휴장일 데이터.

## 4. 수집 설계

1. **증분 수집**: 이미 받은 날짜는 건너뛴다 (`sync_prices`). 과거 데이터는 영구 캐시, 최근 데이터는 유효 기간을 둔다.
2. **단계별 실패 처리**: 한 단계 실패가 전체 스캔을 멈추지 않게 한다. 실패한 단계는 경고로 남기고 관련 항목은 N/A.
3. **대체 경로**: 1차 소스 실패 시 2차 소스 (이번: pykrx 지수 → FDR).
4. **호출 예산**: 종목 수 × 호출 수 × 소요 시간을 추정하고, 제외 필터에 걸린 종목은 무거운 데이터를 받지 않는다 (이번 DART 처리 방식).
5. **응답 검증**: 컬럼 이름·타입·행 수를 확인하고, 기대와 다르면 "어느 단계, 어떤 컬럼이 없음"을 오류에 담는다. 이번 `'지수명'`, `'비중'` KeyError는 이 검증이 있었다면 바로 원인이 보였다.
6. **[보강] 응답 녹화**: 개발 모드에서 실제 응답을 `tests/fixtures/`에 저장하는 옵션.

## 5. 계산 엔진 설계

- 판단 규칙서의 항목 ID(S01, M17, L09, K1, D4 …)를 코드에서 그대로 쓴다. 문서와 코드를 1:1로 찾을 수 있다.
- 항목마다 `(점수, 원천값, 근거 문구, 추정 여부)`를 돌려준다. 화면에서 "왜 이 점수인가"를 보여줄 수 있다.
- 가중치·기준값은 코드 상수가 아니라 설정(프로파일별)에서 읽는다. 권장값은 기준서에서.
- 수동 입력은 자동값을 덮어쓰되, "수동" 표시와 입력일을 남긴다.
- [보강] 계산 결과에 **기준서 버전과 설정 해시**를 남겨서, 나중에 같은 점수를 재현할 수 있게 한다.

## 6. 작업 실행 설계

- 스캔은 백그라운드 작업으로 실행하고, 진행률·현재 단계를 상태 API로 제공한다 (이번 `/api/scan/status`).
- 동시에 두 스캔이 돌지 않게 잠근다.
- 긴 작업은 중간 결과를 저장해서 중단 후 이어 할 수 있게 한다. [보강]
- 스케줄은 앱 안(APScheduler)과 OS 스케줄러(`run.py --scan`) 두 가지를 지원한다. 앱이 꺼져 있으면 앱 안 스케줄은 돌지 않는다는 점을 문서에 밝힌다.

## 7. 설정·비밀값

| 종류 | 저장 위치 |
|---|---|
| 사용자 설정 (스캔 시각, 프로파일, 가중치) | DB `settings` |
| 비밀값 (KRX 비밀번호, API 키) | [보강] OS 키체인 또는 `.env` (권한 600, `.gitignore`), DB에 평문 저장 금지 |
| 시장 규칙 (장 종료 시각, 휴장일) | [보강] 설정 파일/데이터, 코드 상수 금지 |

## 8. 확장 포인트 (처음부터 자리만 만들어 둘 것)

- 알림 채널 (메일, 텔레그램)
- 데이터 소스 어댑터 인터페이스 (pykrx ↔ 증권사 API 교체)
- 내보내기 형식 (CSV/XLSX/MD — 이번에 구현됨)
- 다중 사용자 (지금 필요 없으면 "하지 않음"으로 명시)
