# 01. 프롬프트(요청) 작성 표준

> 목적: Claude(또는 개발자)에게 일을 맡길 때 한 번에 정확하게 전달해서 왕복을 줄인다.
> 이번 프로젝트에서 왕복이 생긴 원인: 목록 누락("아래 기준들"), 표시 방식 변경 3회, 사양 재변경(초단기 비중, 스캔 번호), 동작 문의 5건.

---

## 1. 기본 원칙

1. **무엇을, 왜, 어디까지.** 기능만 말하지 말고 이유(사용 상황)와 범위(하지 말 것)를 같이 쓴다. 이번에 "프로파일을 바꿀 때마다 데이터를 다시 받는 것은 낭비이므로"라는 이유가 붙은 재계산 요청은 한 번에 좋은 설계로 이어졌다.
2. **한 요청에 한 주제.** 서로 관계없는 요청 5개를 한 메시지에 넣으면 하나가 빠지기 쉽다. 묶을 때는 번호를 붙인다.
3. **확인 기준을 쓴다.** "됐다"를 어떻게 확인할지(예: "같은 날 3번 스캔해도 차트에 점 하나")를 쓰면 검증까지 같이 된다.
4. **질문과 수정 요청을 구분한다.** 이번처럼 "(소스 수정이 아니고 문의임)"을 붙인 것은 아주 좋은 습관이다.
5. **모르는 것은 모른다고 쓴다.** "시세 데이터는 아는 것이 없는데 무료로" 같은 표현은 선택을 맡기는 명확한 신호다. 대신 결과에서 선택 근거를 확인한다.
6. **표시 방식은 예시로.** 색·아이콘·위치는 말보다 예시(그림, 다른 사이트 캡처, 이모지)가 정확하다.

## 2. 요청 유형별 템플릿

### 2-1. 새 프로젝트 시작 (킥오프)

```
[목표] 무엇을 하는 프로그램인지 한 문장. 측정 가능한 성공 기준 1~3개.
[사용자] 누가, 언제, 어떤 기기로 쓰는지.
[실행 환경] 웹/데스크톱/모바일, OS, 내 PC에서만/여러 기기에서 접속.
[데이터] 쓰고 싶은 데이터와 출처(모르면 "무료 우선 추천"), 비용 상한.
[판단 규칙] 점수·신호 규칙 문서 위치 (없으면 "같이 만들자").
[필수 기능] 번호 목록.
[하지 않을 것] 자동 매매 안 함, 회원가입 없음 등.
[결과물] 저장소, 실행 방법, 문서, 화면 캡처.
[확인 방법] 내가 무엇을 보면 완료로 볼지.
```

### 2-2. 기능 추가

```
[기능] 무엇을 (메뉴명/버튼명은 따옴표로 정확히)
[이유] 어떤 상황에서 왜 필요한지
[화면] 어느 화면, 어느 위치, 비슷한 기존 화면
[동작] 누르면 무엇이 일어나는지, 기본값
[데이터 없음] 데이터가 없거나 처음 쓸 때 어떻게 보일지 (모르면 "추천해줘")
[범위 밖] 이번에 하지 않을 것
[확인] 이렇게 되면 완료
```

이번 투자검증 요청은 이 형식에 가까워서(메뉴명, 기본 기준일, 화면 재사용, 평가 기준은 현재 기준 적용, 보유 종목 표시 방식) 큰 기능인데도 한 번에 구현되었다.

### 2-3. 버그 신고

```
[현상] 무엇을 했더니 무엇이 나왔다 (화면 캡처 또는 오류 메시지 전체 복사)
[기대] 원래 어떻게 되어야 하는지
[환경] 기기/OS/Python 버전, 마지막 업데이트(git pull) 시점
[재현] 매번/가끔, 특정 날짜·종목에서만
[로그] 스캔 기록 메시지, 터미널 출력 (앞뒤 20줄)
```

이번 프로젝트의 버그 신고는 traceback을 통째로 붙여서 원인 파악이 빨랐다. 계속 그렇게 하면 된다.

### 2-4. 표시·디자인 변경

```
[대상] 어느 화면의 어느 요소
[지금] 현재 모습 (캡처)
[원하는 모습] 예시 그림/이모지/색 코드, 마우스 올렸을 때 문구
[규칙] 구간·기준값 (예: 25%씩 4단계)
[선택지 요청] 확실하지 않으면 "시안 2~3개 보여줘"
```

### 2-5. 동작 문의

```
(소스 수정 아님) [화면/기능]에서 [무엇]의 의미/계산 방식/영향이 궁금함.
답변 형식: 한 줄 요약 + 계산식 + 값을 바꾸면 생기는 일.
```

### 2-6. 판단 규칙(평가 기준) 작성 요청

```
[관점] 단기/중기/장기, 보유 기간
[항목] 항목명, 측정 지표, 점수 구간, 가중치
[데이터] 항목별 데이터 출처, 무료로 구할 수 없으면 처리 방법(N/A, 수동, 대체 지표)
[제외 조건] 아예 채점하지 않을 조건
[등급] 등급 구간, 게이트
[검증] 이 기준이 맞는지 어떻게 확인할지 (백테스트 기간, 비교 지수)
```

## 3. Claude에게 기대할 응답 형식 (Claude 쪽 표준)

요청을 받는 쪽도 아래를 지킨다.

1. **가정한 내용을 맨 앞에.** 요청이 비어 있거나 모호하면 합리적인 기본값으로 진행하고 "이렇게 가정했다"를 쓴다. (이번 "아래 기준들" 건은 잘 처리됨)
2. **검증한 것과 못 한 것을 구분.** "데모 데이터로 확인, 실데이터는 미확인"처럼.
3. **사용자가 할 일을 순서대로.** `git pull` → 재시작 → 지금 스캔 1회 등.
4. **근거 위치.** 계산 방식을 설명할 때는 파일·행 번호.
5. **되돌릴 수 없는 일은 먼저 묻기.** 데이터 삭제, 저장소 공개, 외부 발송.

## 4. 금지·주의 표현

| 피할 표현 | 문제 | 바꿔 쓰기 |
|---|---|---|
| "손실 없는 투자" | 불가능한 목표, 검증 불가 | "6개월 최대 낙폭 -15% 이내 종목 비율 높이기" |
| "아래 기준들도" (목록 없음) | 범위 불명 | 목록을 붙이거나 "설정 화면 전체" |
| "적당히", "보기 좋게" | 기준 없음 | 색·크기·예시 |
| "좋은 종목 추천해줘" | 판단 위임, 책임 불명 | "기준서 규칙으로 채점한 상위 N개" |

## 5. 요청 전 1분 점검

- [ ] 메뉴·버튼·항목 이름을 정확히 썼는가
- [ ] 이유를 한 줄 썼는가
- [ ] 데이터가 없을 때 동작을 생각했는가
- [ ] 완료 확인 방법이 있는가
- [ ] 질문인지 수정 요청인지 밝혔는가
- [ ] 이전에 정한 내용과 충돌하지 않는가 (결정 기록 확인)
