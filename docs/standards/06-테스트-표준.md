# 06. 테스트·검증 표준

> 이번 프로젝트의 가장 큰 공백: 자동 테스트 없음, 실데이터 미검증. 실데이터 버그 4건(지수명, bytes, 공매도 '비중', None 비교)을 모두 사용자가 발견했다.
> 금융 프로그램은 "프로그램이 맞게 도는가"(소프트웨어 테스트)와 "판단 규칙이 맞는가"(전략 검증) 두 가지를 모두 테스트한다.

---

## 1. 테스트 단계 한눈에

| 단계 | 무엇을 | 언제 | 데이터 | 이번 프로젝트 |
|---|---|---|---|---|
| ① 단위 테스트 | 항목 점수 함수, 지표 계산, 형식 변환 | 매 커밋 (CI) | 손으로 만든 작은 입력 | 없음 |
| ② 계약 테스트 | 외부 응답 형식 (컬럼·타입) | 매 커밋 + 주 1회 실데이터 | 녹화한 실제 응답 | 없음 |
| ③ 통합 테스트 | 데모 스캔 전체, 화면 200 응답 | 매 커밋 | 데모 데이터 | 수동으로만 |
| ④ 경계 테스트 | 빈 데이터, 첫 실행, 휴장일, 장중 | 매 커밋 | 조작한 데이터 | 버그 후 수동 |
| ⑤ 실데이터 스모크 | 실제 KRX·DART로 스캔 1회 | 출시 전, 의존성 업데이트 후 | 실데이터 | **사용자가 대신함** |
| ⑥ 화면 테스트 | 주요 화면 캡처, 클릭 흐름 | 화면 변경 시 | 데모 | 캡처로 확인 (좋음) |
| ⑦ 전략 검증 | 백테스트, 등급별 성과 | 기준 변경 시 | 과거 실데이터 | 투자검증 메뉴 (단일 기준일) |

## 2. 단위 테스트 기준

- 판단 규칙서의 **계산 예시**를 그대로 테스트로 만든다. 기준서 13장 예시 → `test_framework_example()`.
- 항목마다 구간 경계값 테스트: 점수 구간 경계에서 "낮은 쪽 점수"(보수적 판단 원칙)가 나오는지.
- N/A 재배분: 일부 항목 N/A일 때 분모에서 빠지는지.
- 게이트: 커버리지 미달 시 89/79점으로 내려가는지.
- 제외 필터 K1~K10 각각.
- 형식 변환: numpy 타입 → 파이썬 타입, NaN → None.

```python
def test_coverage_gate_caps_S_to_A():
    r = finalize(final=93.0, coverage=0.62, s_min=0.80, a_min=0.70)
    assert r.score == 89 and "S 제한" in r.note
```

## 3. 계약 테스트 (외부 데이터 형식)

1. 실데이터에 접근 가능한 곳(사용자 PC)에서 응답을 녹화한다: `python run.py --record-fixtures`.
2. 녹화한 응답(작게 줄인 표본)을 `tests/fixtures/`에 저장.
3. 테스트는 수집기의 파싱 코드가 이 표본을 처리하는지 확인.
4. 주 1회(또는 의존성 업데이트 시) 실데이터로 같은 검사를 다시 돌려 형식 변경을 일찍 발견.

**개발 환경에서 실데이터에 접근할 수 없으면** (이번 클라우드 환경처럼):
- 그 사실을 첫 결과 보고에 명시한다 (이번에는 명시함, 좋음).
- 사용자 PC에서 원격 실행 세션을 열거나, 사용자에게 스모크 테스트 명령 하나를 요청한다.
- 실패 메시지가 "어느 단계, 어떤 컬럼"을 담도록 해서 한 번의 왕복으로 고칠 수 있게 한다.

## 5. 전략 검증(백테스트) 표준

백테스트 결과는 쉽게 사람을 속인다. 아래 점검표를 통과하지 못하면 결과를 "참고용"으로만 표시한다.

### 5-1. 필수 점검표

- [ ] **미래 정보 차단(look-ahead)**: 공개일 ≤ 기준일인 데이터만 썼는가 (재무 공시 시차, 수정된 재무, 현재 업종 분류, 현재 관리종목 목록, 현재 수동 입력)
- [ ] **생존 편향(survivorship)**: 기준일 당시 상장되어 있었고 그 후 상장폐지된 종목도 포함했는가. 현재 상장 목록으로 과거를 고르면 성과가 부풀려진다.
- [ ] **거래 비용**: 수수료(약 0.015%), 증권거래세(매도 시, 연도별 세율 확인), 슬리피지를 반영했는가. 단기 프로파일일수록 영향이 크다.
- [ ] **수정 주가**: 배당·분할·병합을 반영한 가격으로 수익률을 계산했는가
- [ ] **여러 기준일**: 한 날짜가 아니라 최소 12개 이상 기준일(예: 매월)의 평균·분산을 보았는가
- [ ] **벤치마크**: 같은 기간 KOSPI/KOSDAQ, 동일가중 전체 종목 평균과 비교했는가
- [ ] **표본 외 검증**: 기준을 조정한 기간과 검증 기간을 나눴는가 (과최적화 방지)
- [ ] **위험 지표**: 평균 수익률뿐 아니라 최대 낙폭(MDD), 변동성, 승률, 손익비를 보았는가
- [ ] **등급 단조성**: S > A > B > C 순으로 성과가 나오는가. 아니면 기준이 의미 없다.
- [ ] **근사 표시**: 근사한 부분(이번: 기준일 이후 수급·재무 고정)을 화면과 문서에 밝혔는가

### 5-2. 이번 투자검증 메뉴의 현재 수준

| 점검 | 상태 |
|---|---|
| 미래 정보 | 재무는 기한 기준 근사로 차단. 수동 입력·보유/제외 목록은 현재 값 사용 (README에 명시) |
| 생존 편향 | 기준일의 시가총액 목록(`collector.py` 213행)으로 종목을 고르므로 대체로 차단됨. 다만 이후 상장폐지 종목은 마지막 종가로 계산해 폐지 손실이 작게 잡힐 수 있음 |
| 거래 비용 | 미반영 (README에 명시) |
| 여러 기준일 | 단일 기준일 |
| 위험 지표 | 기간 중 최대 상승·하락(종가 기준) 있음 |
| 등급 단조성 | 등급별 평균 수익률 표시 있음 → 확인 가능 |

다음 개선 우선순위: 다중 기준일 반복 → 거래 비용 → 상장폐지 종목 처리.

### 5-3. 검증 보고서 템플릿

```
# 기준서 vX.Y 검증 보고서 (작성일)
- 프로파일 / 보유 기간 / 기준일 목록
- 등급별: 종목 수, 평균·중앙 수익률, 승률, MDD, 시장 대비
- 상위 N개 포트폴리오 vs 벤치마크 (누적 수익 그래프)
- 비용 반영 전/후
- 한계와 근사
- 결론: 기준 유지 / 조정 (조정 시 다음 기간으로 표본 외 검증)
```

## 6. CI 구성 (GitHub Actions 예)

```yaml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.11" }
      - run: pip install -r requirements.lock pytest
      - run: pytest -q
      - run: python run.py --scan --demo   # 데모 스캔이 끝까지 도는지
```
